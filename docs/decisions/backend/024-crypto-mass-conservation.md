# 024 — Crypto Mass Conservation (CMC) Architecture & Coverage Accounting

## Status

ACCEPTED (Track A1 / v1.0, 2026-09-21). Defines the mathematical accounting mechanism, extraction independence invariant, and empirical kill test acceptance criteria for Crypto Mass Conservation (CMC).

## Context

In static cryptographic discovery across enterprise estates, standard evaluation metrics like Precision, Recall, and F1 rely on labelled benchmarks with known ground truth. However, in real-world, unlabelled customer codebases and binary estates:
1. **Ground truth is unknown**: There are no pre-existing annotations of what cryptographic assets exist.
2. **Recall is unmeasurable**: The denominator `TP + FN` cannot be computed because False Negatives (unmodelled, custom, or obfuscated crypto implementations) are unknown by definition.
3. **Absence of findings is not evidence of absence**: A scanner reporting zero findings cannot distinguish between clean code and completely blind detection.

To solve this, ECDAT introduces **Crypto Mass Conservation (CMC)**, treating cryptographic evidence as conserved mass across extraction, attribution, and residual accounting.

## The Conservation Invariant

Every scanned artifact is analyzed for total cryptographic suspicion mass ($M_{\text{total}}$) derived from statistical, structural, and semantic signals. The mass conservation invariant strictly holds:

$$M_{\text{total}} = M_{\text{attributed}} + M_{\text{excluded}} + M_{\text{residue}}$$

Where:
- **$M_{\text{attributed}}$**: Suspicion spans successfully claimed and classified by registered detection rules (producing verified findings).
- **$M_{\text{excluded}}$**: Spans explicitly dismissed with auditable cryptographic rationale (e.g., test fixtures, non-crypto hashing in compilers, benign random number generators).
- **$M_{\text{residue}}$**: Unclaimed suspicion spans. Residue represents potential false negatives or unknown cryptographic implementations requiring investigation or new rule authoring.
- **Coverage Ratio**: $\mathcal{C} = \frac{M_{\text{attributed}}}{M_{\text{total}} - M_{\text{excluded}}}$ (bounded in $[0, 1]$).

## Extraction Independence Invariant

To prevent circular reasoning where detectors only find what they are programmed to look for, the extraction layer (`backend/engine/extract/`) is strictly independent of the rule engine (`backend/engine/rules/`):
- **Rule-Agnostic Extraction**: Extractors identify candidate suspicion spans purely via low-level primitives:
  - `arx.py`: Addition-Rotation-XOR sequences typical of stream ciphers and hash functions.
  - `bigint.py`: Multi-precision arithmetic, modular exponentiation, and Montgomery multiplication loops.
  - `entropy.py`: High-entropy byte sequences and bit-distribution anomalies.
  - `framing.py`: ASN.1, DER, PEM, and PKCS envelopes.
  - `literals.py`: Cryptographic key-length constants and round parameters.
  - `tables.py`: S-box bijections, permutations, and fixed round constant tables.
- **Strict Architectural Boundary**: Code under `backend/engine/extract/` must **never** import from `backend/engine/rules/` (`from engine.rules` or `from ..rules`). Extractors observe evidence; rules interpret evidence.

## Acceptance Criteria: The Four Kill Tests

CMC's validity as an audit-grade metric is guarded by four empirical "Kill Tests" implemented in `backend/tests/test_kill_tests.py`:

1. **K1 — Sensitivity**:
   - *Requirement*: On a labelled corpus of known unmodelled/custom crypto implementations, $\ge 90\%$ of known false negatives must surface as residue in the ledger.
   - *Rationale*: Proves that residue genuinely captures unseen crypto rather than missing it silently.

2. **K2 — Specificity**:
   - *Requirement*: Benign non-cryptographic artifacts (e.g., standard business logic, plain web apps) must produce residue strictly below a pre-defined floor ($< 5.0\%$ mass / 0 residue).
   - *Critical Enforcement*: **If K2 fails, the coverage certificate cannot be trusted and must NOT be shipped.** High residue on benign code would cause alert fatigue and invalidate the coverage ratio.

3. **K3 — Non-Vacuity**:
   - *Requirement*: Disabling an active detection rule must cause its claimed evidence to immediately reappear as residue in the ledger. Re-enabling the rule must return residue to the exact prior value.
   - *Rationale*: Confirms that attribution directly consumes suspicion mass and that the ledger is fully conservative and deterministic.

4. **K4 — Directional Validity**:
   - *Requirement*: Closing residue clusters by authoring new detection rules must measurably increase recall and decrease residue.
   - *Rationale*: Demonstrates that residue serves as an effective operational worklist for improving estate coverage over time.

## Consequences

- Every CBOM generated by ECDAT embeds an auditable Coverage Certificate backed by this conservation model.
- Residue is surfaced directly in the UI (`/residue`), enabling security teams to triage unclassified cryptographic mass before audit sign-off.
- The CI/CD pipeline enforces all four kill tests on every commit, preventing regressions in CMC accounting.
